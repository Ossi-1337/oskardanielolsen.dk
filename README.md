# oskardanielolsen.dk

oskardanielolsen.dk is a portfolio website for displaying projects and profile
links.

The site uses plain HTML, CSS, and JavaScript with no runtime dependencies.

## Styles and asset versions

Cloudflare runs `node scripts/version-assets.mjs` automatically for production
and preview deployments. It embeds `public/index.css` and the contact SVGs from
`public/icons/` into the page, updates that exact stylesheet's SHA-256 CSP
allowance in `public/_headers`, and versions the JavaScript URL (`?v=…`). CSS
and SVGs stay editable in their own files; visitors need no separate stylesheet
or contact-icon requests. Run `node scripts/version-assets.mjs --check` to verify
that the embedded styles/icons, CSP hash, and asset versions are current. For local previews,
run the script after editing source assets; deployment builds regenerate these
files automatically, so manually running it is not required before deploying.

The Cloudflare Pages build command is `node scripts/version-assets.mjs`, with
the repository root as the working directory and `public` as the build output
directory. This generates styles, CSP hashes, and asset versions on every
Git-integrated deployment without installing dependencies.

HTML is not cached, so each response receives a fresh CSP nonce and current
embedded styles/icons. JavaScript can stay in the browser cache for one day. A normal
visit or reload picks up deployed updates without a hard refresh; an already
open page does not update itself.

## Content Security Policy

`functions/_middleware.js` generates a cryptographically random 256-bit nonce
for every HTML response, including Pages' HTML fallback routes. Cloudflare reads
the nonce from the CSP response header and attaches it to its injected
[JavaScript Detections scripts](https://developers.cloudflare.com/cloudflare-challenges/challenge-types/javascript-detections/#if-you-have-a-content-security-policy-csp).
The site's external script remains allowed by `'self'`. Arbitrary inline scripts,
inline event handlers, and third-party scripts remain blocked; there is no
`unsafe-inline`, `unsafe-eval`, fixed nonce, or static script hash allowance.
The embedded stylesheet has one exact SHA-256 allowance under `style-src`;
unapproved inline styles and style attributes remain blocked.

HTML uses `no-store` for browsers and CDNs. The middleware strips conditional and
range request headers and removes HTML validators so an older body cannot be
combined with a fresh CSP nonce. It sets CSP and Permissions Policy itself,
because `_headers` rules are not applied to responses generated by Functions.
It preserves the CSP from the downstream static asset response, including the
generated style hash, while adding the script nonce. A restrictive self-only
policy is used if no downstream CSP is available.

`public/_routes.json` invokes Functions for HTML and API requests and excludes
each existing static asset by its exact path. Keep that list current when adding
assets. Avoid directory-wide exclusions: a missing asset can return Pages' HTML
fallback, which also needs a nonce. HTML requests now count toward Pages
Functions usage; the excluded assets keep their static serving and caching.

After deploying through the normal repository workflow, use Pages **Settings >
Runtime > Fail open / closed** to select **Fail closed** if it is not already set.
This prevents the platform from bypassing nonce generation if the Functions
allowance is exhausted. Keep HTML out of any dashboard Cache Everything or
Edge Cache TTL override that ignores the response's `no-store` headers.

Verify on the deployed custom domain that two HTML requests have different
`'nonce-…'` values, injected Cloudflare scripts carry the matching nonce, and
unapproved inline scripts remain blocked. Local development cannot reproduce
Cloudflare's edge injection. Browser extensions may still produce CSP errors
when attempting to inject scripts; do not allow those scripts just to hide errors.

## Performance

The stylesheet is small enough to embed without a second blocking request.
In a five-run local comparison with 150 ms latency and 4× CPU slowdown, median
first/largest paint changed from 492 ms to 308 ms on cold loads. Warm loads were
similar (212 ms versus 216 ms), with zero layout shift in both versions. These
are controlled lab results, not measured production speed gains.

The stylesheet tradeoff is about 1.7 KiB more Brotli-compressed HTML on each visit instead
of a separately cached stylesheet. The cold HTML-plus-CSS payload shrank from
about 3.0 KiB to 2.9 KiB before response headers. The layout is unchanged.

The two contact icons are embedded from their existing SVG source paths and
use `currentColor`, removing two more requests without extra CSP allowances.
Compared with external icons, this adds about 0.5 KiB to repeat-visit HTML while
reducing cold HTML-plus-icon bodies from 3,552 to 3,364 Brotli bytes, before
headers. In a five-run local comparison with applied mobile throttling, icons
were available with first paint instead of waiting for separate responses;
text LCP and warm-load timing were effectively unchanged.

For live audits, use Lighthouse's `--throttling-method=devtools --save-assets`
options to apply network and CPU throttling during loading and retain the trace.
Compare medians from at least three runs with the same browser, Lighthouse
version, and settings. Keep CSP and Cloudflare protection enabled.

Lighthouse's default [simulated timings](https://github.com/GoogleChrome/lighthouse/blob/main/docs/throttling.md)
are estimates; distinguish them from observed trace timings. In the 2026-10-31
Lighthouse 13.5.0 comparison, the model assigned a new connection to a reused
Cloudflare HTTP/3 request, inflating estimated LCP by about 300 ms. The recorded
paint did not regress. Do not compare simulated and applied-throttling results
as equivalent measurements.
